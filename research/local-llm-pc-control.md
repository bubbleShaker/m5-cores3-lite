# 声で PC を制御するローカル LLM 対話（調査まとめ）

epic: #215 / 調査日: 2026-07-26

「CoreS3 に話しかけて PC を操作する。推論は外部 API ではなく手元で完結させる」を実現するための
構成・モデル選定・セキュリティ設計の調査結果。

## 結論（先に）

- **実機側はほぼ変更不要。** 録音 → `/stt` → `/chat` → `/tts` の一巡はすでに動いている
  （`src/main.cpp:1084-1099`・P2 M3b-2 / #55・#60）。作業はほぼ全部 relay 側。
- **ローカル LLM は relay 側（Windows）に Ollama を置く**のが正解。マイコン上で動かす案は使えない（後述）。
- **relay は現在ノーガード**で、PC 制御を足す前から既に穴になっている。認証を最優先で入れる（#216）。

## 構成

```mermaid
flowchart LR
  A[CoreS3 マイク録音] -->|WAV| B[/stt Whisper]
  B -->|テキスト| C[/chat]
  C -->|プロンプト+ツール定義| D[ローカル LLM Ollama on Windows]
  D -->|関数名+引数| E[ディスパッチャ ホワイトリスト検証]
  E -->|許可されたものだけ| F[PC 操作 アプリ起動・ウィンドウ]
  E -->|返答文| G[/tts VOICEVOX]
  G -->|WAV| A
```

relay を **Windows 側で動かす**のは既存の運用どおりで、今回はそれが必然になる。
制御対象の PC が Windows なので、実行層が同じ OS に居ないとウィンドウを掴めない。
（VOICEVOX は WSL の docker、Whisper も docker。LLM を Windows に置いても構成は崩れない）

## 既存資産の棚卸し

| 部品 | 場所 | 状態 |
|---|---|---|
| `/chat` | `relay/src/chat.ts` + `server.ts` | Claude API。**純粋ロジックとネットワーク層が分離済み** |
| `/tts` | `relay/src/tts.ts` | VOICEVOX（WSL docker・50021）。ずんだもん既定 |
| `/stt` | `relay/src/stt.ts` | 自前ホスト Whisper（docker・9000） |
| 実機の一巡 | `src/main.cpp:1084-1099` | 録音→文字起こし→返答→発話が動作済み |

`chat.ts` がプロンプト組み立てと応答検証（`expression` / `action` の語彙チェック）を
**ネットワーク非依存の純粋ロジック**として持っているのが効いていて、
推論先を差し替える時に**触るのは HTTP を張る層だけ**で済む。

## モデル選定

| 項目 | 値 |
|---|---|
| GPU | NVIDIA GeForce RTX 2070 with Max-Q Design / VRAM 8GB |
| 候補 | Qwen2.5 7B Instruct Q4_K_M（約 4.7GB） |
| 選定理由 | 日本語と tool calling（関数呼び出し）の両立。8GB VRAM に文脈込みで収まる |

⚠ **ドライバが古い。** `nvidia-smi` の報告は **430.81 / CUDA 10.2**（2019 年）。
Ollama の GPU 実行には更新が要る。未更新でも CPU で動作はするが、7B は数 tok/s 程度で
会話には遅すぎる。**#217（M1）の着手前提**として扱う。

## セキュリティ設計

### 1. LLM にシェルの文字列を作らせない

これが設計の一線。選ばせるのは「列挙された関数名 + 型検証済みの引数」だけにする。

```
NG: {"command": "start chrome.exe && rm -rf ..."}
OK: {"name": "launch_app", "args": {"app": "browser"}}
```

理由: **STT は聞き間違えるし、LLM は幻覚を出す。** 前段が 2 つとも確率的なので、
「正しく動くこと」に賭けた設計は必ず破れる。列挙型に閉じ込めれば、
どちらが暴走しても**定義外の操作が構造的に起き得ない**。

`app` に入れてよい値は設定ファイルで列挙する。**実行ファイルのパスは設定ファイル側にしか存在せず、
LLM が触れるのはキー（`browser`）だけ**にする。

### 2. relay の認証（既存の穴）

現在 relay は全エンドポイントが無認証。**PC 制御と無関係に、すでに問題がある**。

- `/chat` は `ANTHROPIC_API_KEY` を保持したまま無認証で叩ける → 同じ LAN の誰でも課金できる
- 公衆 Wi-Fi で 8080 の受信をファイアウォールで開けた運用実績がある

この上に PC 操作を足すと「LAN にいる誰でも PC を操作できる」になるため、
共有トークン認証を**最優先**で入れる（#216）。トークン比較は `crypto.timingSafeEqual` を使う
（素朴な文字列比較はタイミング攻撃の的になる）。

### 3. 実行層の作法

- コマンドを**文字列連結で組み立てない**。実行ファイルと引数は配列で渡す（`execFile` 系。`exec` は使わない）
- 破壊的操作（ファイル削除・シャットダウン・任意コマンド実行）は初期スコープに入れない
- 監査ログ: いつ・どの発話から・どのツールを・どの引数で実行したかを記録する

## 却下した案: マイコン単体で LLM を動かす（esp32-ai）

https://github.com/slvDev/esp32-ai は **ESP32-S3 単体で 28.9M パラメータの推論を完結させる**
プロジェクトで、ハードは N16R8（16MB flash / 8MB PSRAM OPI）＝ **CoreS3-Lite と同スペック**。
Google Gemma 由来の Per-Layer Embeddings で 25M 行の表を遅い flash に置いたまま成立させている。

**本件の目的には使えない。** TinyStories（英語の童話）で学習した「文章の続きを書くだけ」のモデルで、
日本語も対話も tool calling もできない。加えて既存アプリと同居できず（アプリ領域 1MB に対し
現行ファームは 2.08MB）、学習済みモデルも配布されていない。

技術デモとしては面白いので **#221 に温存**した。詳細な数値と障害 4 点はそちらに記載。
