## #207 fps の低下（ペーシングの気づき遅れ）

### 原因
`framePace`（loop 末尾）が全シーン一律に「1 コマ 33ms」へ整えていたため、再生中の軽い周回
（フレーム番号が変わらない周回）の後にも 33ms 寝ていた。結果、**フレーム締切（1/fps 境界）に
最大 33ms 気づき遅れる**。

```
気づき遅れ（最大 33ms）＋ 描画 65〜94ms（#176/#191 実測）> 予算 100ms（10fps）→ コマ落ち
```

JPEG が大きい曲ほど描画が長い（`draw ≈ 41.5ms + 1.43ms/KB`・#191）ので、曲を増やしたら
落ちるようになった、という体感と整合する。

### 対処
- 純粋関数 `video_until_next_frame_ms(elapsed_ms, fps)` を追加（`video_frame_at` と同じ total が
  次に進む時刻までの残り ms。返り値は 1..1000/fps+1 に収まる＝クランプは必ず短くする方向）
- `SceneDef` に `paceLimitMs`（省略可）を追加。`framePace` はシーン表経由で締切を問い合わせ、
  寝る長さを `min(33 - spent, 締切)` にする
- **共通機構に動画固有の状態を持ち込まない**ため、依存を「framePace → 動画」から
  「動画 → 共通機構の口」へ反転させた（reviewer 指摘）

### 副作用（良い方）
再生中のタッチサンプリング間隔も短くなるので、長押しの反応が少し良くなるはず。

## #208 再生開始のラグ（数秒 → 約 0.3 秒の見込み）

### 原因の内訳
| 処理 | 時間 |
|---|---|
| `videoLoadAudio` が audio.wav（`aaa` は 6.78MB）を **1 回の read で丸ごと**読む | 約 3〜6 秒（支配的） |
| `videoBenchLcd`（#176 の計装・pushSprite 30 回 × 34.1ms ＋ Sprite 確保） | 約 1.1 秒 |
| meta 読み・索引 19KB・1 枚目描画 | 0.2 秒弱 |

### 対処
1. **`videoBenchLcd` を撤去**。#176/#191 で「30fps 却下」と内訳分解という役目を終えている。
   必要になったら PR #180 から戻せる。
2. **音声のチャンクストリーミング化**:
   - ヘッダ＋先頭チャンク（64K サンプル＝128KB ≈ 4.1 秒ぶん）だけ同期で読んで即再生開始
   - 残りは再生中の毎周回、`videoAudioStep` が**次フレーム締切までの余り時間の予算内**で読み足す
     （#207 で直したコマ落ちを別経路で再発させないため）
   - 読めたチャンクを Speaker のチャンネルキュー（再生中＋次の 1 本）へ順次投入。PSRAM
     バッファ内のポインタを渡すだけでコピーは無い

```
旧: [====== 6.78MB 全部読む（数秒） ======] → 再生開始
新: [128KB] → 再生開始 → 以降は空き時間に少しずつ読み足し
```

### 🔴 レビューで見つかった重要な回帰（修正済み）
**`M5.Speaker.stop()` は同期停止ではない。** 実装は「全チャンネルの *next スロット* に停止
マーカーを書くだけ」で、実際に止まるのは出力タスクが次に DMA バッファを埋める時。
一方 `playRaw(..., stop_current_sound=false)` はそのスロットを**上書きする**ため、停止指示が消える。

つまり「専用チャンネル固定 ＋ stop=false」にした結果、`videoRestartCycle`（周回）の
`stop()` が握り潰され、**前の周のチャンクが鳴り切るまで最大 4.1 秒、古い音が残る**状態だった。
変更前の `channel=-1`（自動割当）では別チャンネルが選ばれるため構造的に起きなかった。

→ **先頭チャンクだけ `stop_current_sound=true`**（チャンネルを奪う）に変更。呼び出し側の
`stop()` のタイミングに依存しなくなった。M5Unified 側の `_set_next_wav` / `label_next_wav` /
`clear_idx` まで追って、新チャンクが `ch_index=0` から鳴ることも確認済み。

### その他の防御（レビュー指摘の反映）
- **枯渇（underrun）と真の終端を区別**。区別しないと、アンダーランが「音声が早く終わった」という
  嘘の `audio end` ログに化けて、チャンク化で一番怖い故障が見分けられなくなる
- 無音へ落ちた時だけ**予算を無視して読む緊急経路**（`[video] audio emergency read`）。
  高レート素材（44.1kHz stereo 等）や壊れた meta の巨大 fps で「先頭チャンクだけ鳴って無音」に
  落ちるのを防ぐ。発動条件を `==0`（実際に無音になってから）に絞ったのは、`<=1` だと再生開始直後に
  ほぼ必ず成立して曲の頭で再現性のあるコマ落ちを作るため
- SD 読み速度の見積りを実測 1.1MB/s の **0.6 倍**（600B/ms）に。実運用は frames.bin の seek+read と
  交互に叩くので実測どおりには出ない
- `videoReleaseAudio` は free の前に鳴り終わりを待つ（非同期停止の窓での use-after-free 対策）
- WAV の毒入力を拒否: `sample_rate == 0`（再生位置が進まずキューが詰まる）、`channels > 2`

### 実機確認の観点
- タップ→再生開始が体感で速くなったか
- **チャンク継ぎ目のノイズ**（出たら `kVideoAudioChunkSamples` を大きくして継ぎ目を減らす）
- `[video] audio underrun` / `[video] audio emergency read` が出ていないか
- **周回時に音が即切り替わるか**（🔴 の修正が効いているか。古い音が数秒残らないこと）

## #209 曲選択の CD フェード遷移

### 対処
選択画面は既に毎コマ全画面合成している（#199）ので、そこにフェードの状態機械を足した。

```
スワイプ → 160ms フェードアウト → 暗転の底でサムネイル差し替え（SD 読み）→ 160ms フェードイン
```

- **暗転の底で SD を読む**のが要点。数十 ms の読みが一番目立たない瞬間
- `pushRotateZoom` にアルファ合成が無いので、フェードは**元絵からの輝度スケーリング複写**で実現。
  元絵用に 132²×2B ≈ 35KB の PSRAM を持ち、毎コマ `level/256` を掛けて表示用 Sprite へ複写する
- 連打スワイプは**暗転をやり直さず行き先だけ差し替える**（2 回払えば 2 曲進む）。
  フェードイン中のスワイプは「今の明るさ」から連続に折り返す（輝度が跳ばない）
- フェード中の決定タップは「UI が向かっている曲」を選ぶ

### 🔴 レビューで見つかった不具合（修正済み）
「フェード中だけ複写する」実装だと、**完了コマ（level=256）で複写が走らず、最後に適用した
暗い絵が次のスワイプまで残り続ける**。選択画面の 1 コマは約 50ms なので、実際には 62〜94% の
明るさで居座る＝「フェードのたびに暗くなって戻らない」。

→ `video_fade_needs_redraw` を追加し、**kIdle へ落ちた最初の 1 コマだけ true** を返して等倍複写を
1 回させる（`videoDiscFadeApply(256)` は厳密な恒等）。

### もう 1 つの体感バグ（修正済み）
フェードインの起点を「底のコマ」で打つと、その直後の SD 読み（数十 ms）ぶん先に進んでしまい、
**輝度 0 から一気に明るい値へ飛ぶ**（片道 160ms ＝ 約 3 コマしかないので 1 コマの損失が致命的）。
→ `video_fade_rebase` で読み終わりの時刻に起点を打ち直す。

### 色の扱い（この repo が 2 回踏んでいる罠）
Sprite の生バッファは **swap565**（#80・#205 の経緯）。`__builtin_bswap16` で RGB565 に戻してから
R/B（0xF81F）と G（0x07E0）を分けてスケールする定石を使い、透明色 `kDiscTransp` の画素は
スケールせず通す。スケール結果が偶然透明色に一致することは無い（R=31 には level≥256 が要る）。
reviewer が M5GFX の `Panel_Sprite::createSprite`（16bpp は行パディング無し）まで確認済み。

### 次に触る人への申し送り
- **「選択画面へ入る全経路が `videoShowSelect` か `videoDiscUiRelease` を通る」**という不変条件に、
  フェード状態のリセット（`video_fade_init`）が支えられている。選択画面へ入る経路を増やす時は、
  そのどちらかを必ず通すこと。通らないと、解放済み UI 向けの `pending` が後から発火して
  意図しない曲へ切り替わる。
- `videoSelectCompose` が `g_videoSel` の更新と SD 読みまで持っているのは設計として綺麗ではない
  （描画層と状態遷移層の混在）。分離するなら `videoSelectStep(now)` を `videoUpdate` から先に呼び、
  compose は輝度を引数で受ける形になる。今回は影響範囲を見て見送った。
- **フェード中（kOut）のタップは「画面にまだ出ていない曲」を再生する**（最大 160ms の窓）。
  直近の入力を尊重する側に倒した意図的な挙動。違和感が出たら、曲名だけ request 時に先行して
  切り替える（ディスクは底で切り替える）のが最小の修正。

### 実機確認の観点
- フェードが滑らかか（3 コマ程度しかないので、カクつくなら `kDiscFadeMs` を伸ばす）
- **フェード後にディスクが暗いまま残らないか**（🔴 の修正が効いているか）
- 底で「黒い円」が模様の上に見えるのが許容できるか（背景へ溶けるクロスフェードではない）
- 連打スワイプで引っかからないか
- `[video] select` ログの `fade` バケット（底のコマは SD 読みを含むので突出するのが正常）
